This section records the 25 August assessment. The 24 September recheck above found a materially smaller homepage DOM and fewer product links. Further performance conclusions require controlled lab and field measurements. The remaining repeated markup and delivery configuration warrant investigation.

Recommended direction

  • Stop rendering inactive product tabs and large product collections into the initial DOM.

  • Render only the first visible product set (for example 8–12 cards) and fetch additional tabs/sections on interaction or near-viewport.

  • Treat Magento JavaScript/CSS optimization as a second layer after DOM/content architecture is fixed.

  • Audit GTM/analytics initialization and remove duplicate or unnecessary tags.

  • Establish measurable performance budgets and regression checks before and after every release.

5. Detailed Findings

F01 — Excessive initial DOM / page structure

Critical / P0 — The homepage continues to ship a very large amount of catalog markup. A large DOM increases browser memory use and makes style recalculation, layout, paint, and interaction work more expensive.

Evidence / rationale: Current crawl exposes many product nodes consecutively from multiple product families.

  • Google web.dev documents that large DOMs can increase rendering work and contribute to poor interaction responsiveness/INP.

Recommended fix:

  • Rebuild homepage sections around a bounded initial render.

  • Remove hidden/inactive catalog markup from initial HTML.

  • Set an explicit DOM budget and track it in Lighthouse/CI.

F02 — Inactive model-year tabs are pre-rendered

Critical / P0 — The current HTML contains products from multiple years under tabbed groups. Hiding content with CSS does not remove its network, HTML parsing, DOM, style, and memory cost.

Evidence / rationale: GIORNO+ 2024, 2025 and 2026 products are all present.

  • LEAD 2022, 2025 and 2026 products are all present.

  • PCX 2021 and 2022 products are also present in the same initial document.

Recommended fix:

  • SSR only the default active tab.

  • When another year is selected, fetch that dataset/HTML fragment asynchronously and cache it.

  • Optionally prefetch the next most likely tab after load/idle, not during the critical path.

F03 — Too many product cards are delivered on the homepage

Critical / P0 — A homepage should help users discover categories and products, but it should not behave like multiple full category pages concatenated together.

Evidence / rationale: Repeated product titles, prices, inputs and add-to-cart controls dominate the initial document.

  • Previous baseline found 456 product links.

Recommended fix:

  • Cap product cards per section (typically 8–12).

  • Add 'View all' to category/model pages.

  • Use horizontal carousel/virtualized list only if UX requires more choices; do not retain off-screen cards in the DOM indefinitely.

F04 — Repeated purchase controls amplify markup and interaction cost

High / P1 — Each product row/card includes input controls and add-to-cart behavior. Repeating full form structures hundreds of times compounds DOM size and event initialization.

Evidence / rationale: Current crawl repeatedly shows two inputs plus an add-to-cart control for product entries.

Recommended fix:

  • Use minimal card markup.

  • Use event delegation from the product-grid container.

  • Create/initialize quantity or configurable-product UI only on user intent where possible.

  • Preserve CSRF/form-key and Magento cart behavior while reducing duplicated DOM.

F05 — Third-party / GTM duplication risk

High / P1 — The current page crawl exposes two Google Tag Manager iframe references. This does not by itself prove duplicate event firing, but it is a strong signal that the tag stack needs inspection.

Evidence / rationale: Two googletagmanager.com iframe references appear near the start of the document.

Recommended fix:

  • Inventory all GTM containers/snippets in theme, CMS blocks, modules and consent tools.

  • Confirm only the intended container initializes.

  • In GTM Preview/Tag Assistant, verify each page_view/ecommerce event fires exactly once.

  • Remove obsolete pixels and tags; delay non-critical marketing tags until consent/interaction where appropriate.

F06 — JavaScript delivery must be Magento-aware

High / P1 — Magento's frontend is modular. Simply merging JavaScript into one large file can make first-load performance worse and Adobe explicitly warns against deprecated JS/CSS merging patterns.

Evidence / rationale: Adobe recommends advanced/page-type bundling strategies and minification.

  • Adobe notes built-in bundling can still load bundles that a page does not need.

Recommended fix:

  • Run production mode and static-content deployment correctly.

  • Minify JS/CSS/HTML.

  • Do not rely on deprecated JS/CSS merge.

  • Use page-type/purpose-specific bundles or a modern frontend build strategy.

  • Defer non-critical and third-party JS.

F07 — Image loading should be aligned to viewport priority

High / P1 — Catalog-heavy pages often waste bandwidth by downloading below-the-fold product images too early. The homepage should prioritize the hero/LCP image and defer the rest.

Evidence / rationale: Exact image request count/formats were not available from the public crawl; this is a required browser-level verification.

Recommended fix:

  • Use responsive srcset/sizes.

  • Prefer WebP/AVIF where supported.

  • Set explicit width/height to prevent layout shifts.

  • Use loading='lazy' for below-the-fold product images.

  • Do not lazy-load the LCP/hero image; preload/fetchpriority='high' only when justified.

F08 — Full-page caching and delivery configuration require validation

High / P1 — Magento performance depends heavily on correct production caching and delivery. A structurally smaller page should then be served through appropriate FPC/Varnish/CDN layers.

Evidence / rationale: External crawl cannot confirm Magento mode, Varnish, Redis, CDN cache status or origin TTFB.

Recommended fix:

  • Verify production mode.

  • Verify Magento caches are enabled.

  • Use Varnish/full-page cache per supported architecture.

  • Use Redis for cache/session where appropriate.

  • Set immutable/versioned static-asset caching.

  • Place static/media assets behind CDN and verify compression (Brotli/Gzip) and HTTP/2 or HTTP/3.

F09 — No explicit performance budget / regression gate

High / P1 — Without budgets, homepage content tends to grow back after optimization.

Evidence / rationale: Previous baseline is already large and current structure remains similar.

Recommended fix:

  • Define budgets for DOM nodes, document KB, JS KB, image KB, third-party KB, request count and Core Web Vitals.

  • Run Lighthouse CI or equivalent on homepage/category/product/cart/checkout.

  • Block release or require approval when budgets regress.

F10 — Core Web Vitals need field-data validation

Medium / P2 — The structural issues strongly suggest risk to LCP/INP, but the final acceptance decision should use real-user field data plus repeatable lab tests.

Evidence / rationale: No stable current CrUX/PSI result was available in this audit.

Recommended fix:

  • Capture PSI/CrUX at baseline.

  • Instrument web-vitals RUM by page type/device/network where feasible.

  • Use 75th-percentile targets: LCP <=2.5s, INP <=200ms, CLS <=0.1.

  • Compare 28-day field trend after release.

6. Root-Cause Model

Layer Current issue Effect
Content architecture Homepage includes too many product sets Large HTML and product link count
Rendering architecture Inactive tabs exist in DOM Parsing/style/layout cost paid even when hidden
Component markup Repeated controls/forms per product DOM depth and event initialization grow with card count
Frontend assets Magento modules + custom/theme JS can load broadly Main-thread/network cost
Third-party Potential duplicate GTM + marketing scripts Additional requests and main-thread work
Delivery Caching/CDN state not validated Potential server/TTFB and repeat-visit inefficiency
Governance No visible performance budget Regression likely after future merchandising changes

The most important sequencing decision is to fix the top three layers first. Optimizing images, CDN, or minification while continuing to send thousands of unnecessary DOM nodes will improve symptoms but will not remove the main structural bottleneck.

7. How-to-Fix: Implementation Guide

7.1 Rebuild homepage tab rendering (P0)

Desired behavior: server-render only the active/default tab and a small initial product set. Other tabs should be data placeholders until requested.

  1. Identify every homepage block that renders products by model/year.

  2. Change the Magento block/template/view-model so the initial response contains only the active year and a limited number of products.

  3. Expose a lightweight endpoint or GraphQL/REST query that returns the requested model/year product set. Prefer JSON plus a small reusable client template, or a server-rendered fragment if that fits the existing theme.

  4. On tab click, fetch only that tab's products, insert them into the tab panel, then cache the response in memory/browser where appropriate.

  5. Use an AbortController/request guard so rapid tab switching does not stack duplicate requests.

  6. Optionally prefetch only the next likely tab using requestIdleCallback or near-viewport logic after the main content is interactive.

  7. Test add-to-cart, pricing, stock, configurable products, form_key/CSRF, analytics and accessibility after conversion.

Acceptance criteria

  • Inactive tabs contribute zero product-card nodes at initial load.

  • Switching tabs loads content on demand with clear loading/error states.

  • Repeated clicks do not refetch already loaded tabs unless cache invalidation requires it.

  • Keyboard/tab semantics remain accessible (role=tab/tablist/tabpanel or equivalent).

7.2 Reduce homepage product density (P0)

  • Limit each merchandising section to 8–12 initial cards.

  • Move deep browsing to category/model pages.

  • If business requires many sections, progressively reveal sections as they approach the viewport rather than rendering all at document start.

  • Do not use CSS display:none as the primary performance strategy; hidden DOM is still DOM.

7.3 Simplify product-card markup and add-to-cart (P1)

  • Audit the product-card DOM tree and remove decorative wrappers that do not provide layout/accessibility value.

  • Use a single delegated click/input listener per product grid instead of binding handlers to hundreds of cards.

  • Render quantity/configuration controls only when needed; keep simple-product cards minimal.

  • Avoid duplicate IDs and unnecessary hidden inputs.

  • Retain Magento security tokens and server-side validation.

7.4 Magento frontend asset optimization (P1)

Action Recommendation
Mode Run storefront in production mode for production environments.
HTML Enable/minify HTML output where supported and validate no extension conflicts.
CSS Minify; remove unused theme CSS; consider critical CSS for above-the-fold content.
JS Minify and defer non-critical scripts.
Bundling Use page-type/purpose-specific advanced bundling or a modern theme build strategy. Measure first load, not only request count.
Merging Do not rely on deprecated 'merge JS/CSS' as a performance solution; Adobe warns it can conflict with RequireJS and offers little/no benefit on HTTP/2.
Static content Use proper static-content deployment and version/sign static files.
Source maps Disable production source-map delivery unless operationally required.

7.5 GTM / analytics cleanup (P1)

  1. Search Magento theme/layout XML/templates/CMS blocks/modules for GTM container snippets.

  2. Open GTM Preview / Tag Assistant and record all tags firing on one clean homepage load.

  3. Verify one canonical page_view event and one ecommerce event per user action.

  4. Remove old GA/UA/pixels and duplicate containers.

  5. Move non-critical marketing scripts behind consent, idle time or interaction where business/legal requirements permit.

  6. Retest performance with third-party domains blocked to quantify their real contribution.

7.6 Image strategy (P1)

  • Generate correctly sized thumbnail variants at the Magento media layer; do not serve oversized originals into small cards.

  • Use WebP/AVIF variants where the stack supports them.

  • Set intrinsic dimensions/aspect-ratio to control CLS.

  • Lazy-load below-the-fold images; eagerly load only above-the-fold assets.

  • Identify the real LCP image and prioritize only that resource.

Recommended lab procedure

  1. Chrome Incognito or clean profile; clear storage between cold runs.

  2. Mobile emulation with network and CPU throttling; run at least 3–5 times and use median.

  3. Capture Lighthouse JSON plus DevTools Performance and Network HAR for baseline.

  4. Record DOM node count, HTML bytes, total transfer, request count, LCP/INP proxy/TBT/CLS and third-party main-thread time.

  5. Repeat after each remediation phase under the same conditions.

  6. Use PageSpeed Insights/CrUX for field-data validation once enough real-user data accumulates.

11. Expected Improvement

Exact gains must be measured after implementation, but the structural fixes should produce the largest improvement because they remove work rather than merely compress it. The expected order of benefit is:

  1. Remove hidden/inactive catalog DOM and reduce product density.

  2. Reduce card markup and image/network load.

  3. Clean third-party scripts.

  4. Optimize Magento JS/CSS and production caching.

  5. Enforce budgets so performance remains stable as merchandising content grows.

A successful Phase 1 should be visibly reflected in a sharply smaller initial HTML document and DOM count even before any CDN or JavaScript tuning. That is the most useful proof that the root cause has actually been addressed.
